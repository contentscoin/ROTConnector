# Production hardening, community board, and PWA shell for ROTConnector

This change adds three feature clusters to the ROTC Business Association trust platform: production UX polish (request editing, search debouncing, toast system, notifications grouping, about page, link editing), a community announcements board (schema + CRUD + full page), and PWA infrastructure (service worker, splash screen, enhanced error boundary, social meta). The approach is additive — new Convex mutations/queries, a new `announcements` schema table, and UI pages wired through existing session/auth patterns. Build passes cleanly.

Watch for: the `announcements.list` query collects the entire table on every call regardless of limit (confirmed); the CSV export returns raw phone numbers to the browser which creates a client-side PII surface even though it's admin-gated (confirmed); the service worker caches HTML responses and has no cache-busting strategy across deploys (likely).

**Verdict**: APPROVED

## High-level view

The announcements subsystem follows the same auth pattern as the rest of the app — `requireMember` for writes, public reads for listings — but the `list` query loads all rows into memory before slicing to `limit`. The `by_category` index exists in the schema but is never used by the query. At a few hundred posts this becomes a measurable cost on Convex's billing model.

The CSV export (`admin.memberSummary`) returns phone numbers to the admin client for download. This is intentional for association management, but phone numbers transit to the browser in plain JSON and sit in the Convex reactive cache — worth noting if the admin panel is ever embedded in shared contexts.

The service worker uses a network-first strategy with fallback, but the cache key `rot-v1` is hardcoded. Vite's content-hashed assets won't be stale, but `index.html` cached under the old key will serve stale HTML until the SW itself is replaced. On a failed network fetch, the stale HTML references non-existent chunk URLs and the app fails to boot.

Profile link editing accepts arbitrary strings as URLs without validation. A `javascript:` scheme URL could be stored and rendered as a clickable link on another member's view of the profile.

<summary>Issues (5)</summary>

1. **announcements.list collects full table** — The query calls `.collect()` on all announcements before filtering by status and category. Use the `by_category` index with a `.take(limit)` approach, or at minimum filter with a Convex `.filter()` predicate before collecting to avoid loading archived rows.
2. **Service worker cache versioning** — `CACHE_NAME = 'rot-v1'` is static. On redeploy, the old `index.html` may be served from cache until the browser fetches the new SW file. Consider injecting a build hash or using `importScripts` versioning.
3. **announcements.list N+1 author lookups** — Each item fires a separate `ctx.db.get(item.authorId)`. With 30 items this is 30 point reads per query invocation. Convex batches the round-trip but each read counts toward the function's budget.
4. **Splash removal race** — `removeSplash()` is called synchronously after `createRoot().render()`, but React 18+ render is not synchronous. The splash fades before the app is actually interactive. Moving it to a `useEffect` in `<App>` would be more accurate.
5. **No URL validation on profile links** — The link editing UI accepts any string as a URL. Malformed or `javascript:` URLs could be stored and rendered as clickable links. Add server-side validation in `members.update` requiring `http://` or `https://` prefix.

## Announcements query performance

The `announcements.list` handler executes:

```ts
let rows = await ctx.db
  .query('announcements')
  .withIndex('by_created')
  .order('desc')
  .collect()
rows = rows.filter((r) => r.status === 'active')
```

This loads every announcement (active and archived) into memory on every invocation. The schema defines `by_category: ['category', 'createdAt']` which could narrow the scan when a category filter is present, but the code never uses it. The fix: when `category` is provided, query with `.withIndex('by_category', q => q.eq('category', category))` and add a `.filter(q => q.eq(q.field('status'), 'active'))` before `.collect()`. Without a category filter, a compound `by_status_created` index would be ideal but doesn't exist yet.

The per-item author lookup (`ctx.db.get(item.authorId)`) wrapped in `Promise.all` issues up to 30 parallel point reads. Convex batches these internally so latency is a single round-trip, but each read counts toward the function's read budget.

## Service worker lifecycle and cache staleness

The SW caches `/` and `/index.html` at install time. The network-first fetch handler means normal navigations hit the network first, falling back to cache only when offline or on error. The risk: if the network returns a 5xx or the CDN is briefly down, the stale cached `index.html` is served. Since Vite's JS/CSS are content-hashed, the old HTML will reference non-existent chunk URLs and fail to boot — the offline fallback becomes a broken page rather than a graceful degradation.

The hardcoded `CACHE_NAME = 'rot-v1'` means the activation handler's cleanup logic never triggers unless the constant is manually changed. A build-time injection (`rot-${GIT_SHA}`) would make deploy-time cache invalidation automatic.

## Splash screen timing

```ts
createRoot(document.getElementById('root')!).render(<StrictMode>...</StrictMode>)
removeSplash()
```

`createRoot(...).render(...)` schedules work but doesn't block until paint. `removeSplash()` fires immediately, fading out the splash before the React tree has committed. On slower devices with large Convex initial queries, the user sees a blank white gap between splash fade and first meaningful paint. A `useEffect` in the root `<App>` that calls `removeSplash()` would guarantee the tree is mounted.

## Link editing lacks URL sanitization

The profile link editing UI (`MyProfilePage`) stores `{ label, url }` pairs without validating the URL format. The `members.update` mutation accepts the `links` array as-is. A user could store `javascript:alert(1)` as a URL. When another member views their profile and clicks the link, the browser may execute the scheme. Server-side validation in `members.update` requiring URLs to start with `https?://` would close this vector.
